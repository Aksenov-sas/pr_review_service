# PR Reviewer Assignment Service

Сервис для автоматического назначения ревьюверов для Pull Request'ов.

## Архитектура

Сервис построен с использованием clean architecture и включает в себя:

- **HTTP Layer**: Обработчики запросов (handlers)
- **Service Layer**: Бизнес-логика (services)
- **Data Layer**: Хранилище данных (postgres) с PostgreSQL
- **Cache Layer**: Redis для кэширования
- **Interfaces**: Единое место для всех интерфейсов приложения

## Основные возможности

- Создание команд и управление участниками
- Автоматическое назначение ревьюверов для Pull Request'ов
- Возможность переназначения ревьюверов
- Поддержка состояний PR (OPEN/MERGED)
- Массовая деактивация пользователей с безопасной переназначаемостью открытых PR
- Нагрузочное тестирование: Интеграция с k6 и мониторинг через Prometheus/Grafana
- Линтинг кода: настроен golangci-lint для обеспечения качества кода

## Инфраструктура

- **PostgreSQL** - основное хранилище данных
- **Redis** - кэширование часто запрашиваемых данных
- **Docker** - контейнеризация
- **Docker Compose** - оркестрация
- **Prometheus** - мониторинг
- **Grafana** - визуализация метрик
- **k6** - нагрузочное тестирование

## API endpoints

### Команды
- `POST /team/add` - создание команды
- `GET /team/get` - получение команды

### Пользователи
- `POST /users/setIsActive` - установка статуса активности пользователя
- `POST /users/massDeactivate` - массовая деактивация пользователей (новый эндпоинт)
- `GET /users/getReview` - получение PR для ревьювера

### Pull Request
- `POST /pullRequest/create` - создание PR
- `POST /pullRequest/merge` - слияние PR
- `POST /pullRequest/reassign` - переназначение ревьювера

### Мониторинг
- `GET /metrics` - метрики для Prometheus

##Массовая деактивация пользователей

Реализован метод массовой деактивации пользователей команды с безопасной переназначаемостью открытых PR. Особенности:

- **Эндпоинт**: `POST /users/massDeactivate`
- **Параметры запроса**:
  - `team_name`: Имя команды
  - `user_ids`: Список ID пользователей для деактивации
  - `with_reassignment`: Флаг необходимости переназначения PR
- **Оптимизация**: Логика уложена в 100 мс для средних объемов данных
- **Безопасность**: При переназначении учитываются правила (не назначается автор, уже назначенный ревьювер и т.д.)

Пример запроса:
```json
{
  "team_name": "my-team",
  "user_ids": ["user1", "user2", "user3"],
  "with_reassignment": true
}
```

## Установка и запуск

### С помощью Docker Compose

```bash
# Запуск всей инфраструктуры
make compose-up

# Просмотр логов
make logs

# Остановка инфраструктуры
make compose-down
```

### Локальный запуск

```bash
# Установка зависимостей
go mod tidy

# Сборка
make build

# Запуск (требуется запущенный PostgreSQL, Redis)
make run
```

### Запуск тестов

```bash
#Запуск E2E-тестирования
E2E_TESTS=true go test ./test/e2e/ -v

# Запуск линтера
make lint

# Запуск нагрузочного тестирования
make loadtest-basic
make loadtest-edge
make loadtest-all
```

## Нагрузочное тестирование

В проект интегрированы нагрузочные тесты с помощью k6:

## Кэширование

Для ускорения работы часто запрашиваемые данные кэшируются в Redis:

- Информация о командах
- Информация о пользователях

Кэш автоматически инвалидируется при изменении данных.

## Безопасность и отказоустойчивость

- **Graceful shutdown** - корректное завершение работы при получении сигнала
- **Connection pooling** - управление соединениями с PostgreSQL
- **Health checks** - проверка состояния зависимых сервисов в docker-compose
- **Context propagation** - передача контекста во все слои приложения
- **Обработка ошибок** - надежная обработка и логирование ошибок



## Решенные проблемы

### 1. Проблема: Отсутствие эндпоинта для метрик

**Описание**: Нужно было интегрировать Prometheus для мониторинга.  
**Решение**: Добавление эндпоинта `/metrics` и middleware для сбора метрик.


### 2. Проблема: Дублирование кода в PostgreSQL-реализации

**Описание**: Повторяющийся код для сканирования результатов SQL-запросов.  
**Решение**: Вынесение общей логики в отдельный метод `scanPullRequest`.

### 3. Проблема: Необработанные ошибки закрытия ресурсов

**Описание**: Не проверялись ошибки при закрытии соединений и потоков данных.  
**Решение**: Добавление обработки ошибок при закрытии всех ресурсов.

## Дополнительные особенности

- **Мониторинг**: Система метрик через Prometheus и визуализация в Grafana
- **Непрерывная интеграция**: Поддержка CI/CD с проверкой качества кода и тестами
